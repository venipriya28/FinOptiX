## Checklist

### Implemented and working in the archived version

- [x] FastAPI API for health, CSV upload, spend summary/trends, forecast, anomalies, recommendations, what-if, ranking, savings, and keyword copilot.
- [x] Seeded 365-day synthetic dataset with 40 resources and ten explicit scenarios plus anomaly/opportunity labels.
- [x] Pandas validation/feature derivation; cost summary, Isolation Forest, chronological forecast holdout, rule-based suggestions.
- [x] React dashboard pages for overview, explorer/upload, forecast, anomalies, recommendations, simulator, savings, and copilot; data is fetched from the API.
- [x] PostgreSQL schema draft, Compose service definitions, project documentation, backend unit/API tests.

### Partially implemented

- [ ] What-if interface exists, but only one user-selected action is run at a time; no validated alternative catalog or transition matrix.
- [ ] Risk/confidence/ranking fields exist, but are uncalibrated constants rather than historical evidence scores; no savings-only versus risk-aware comparison.
- [ ] Synthetic data includes multiple scenarios, but no held-out scenario evaluation, comparative detector baseline, or action-feasibility experiment.
- [ ] Anomaly evidence compares resource cost with prior median, but no measured spend attribution across resource count/runtime/service/region dimensions or uncertainty.
- [ ] CSV upload exists, but source changes live process memory and rewrites a local file; no transactional persistence or restart-safe storage.
- [ ] Docker Compose starts Postgres and API, but the API does not use Postgres; database health/readiness is not checked.
- [ ] Dashboard has loading/fatal-error states; some secondary fetch/action errors and simulator assumptions are shallow.

### Broken or misleading behavior found

- [ ] Simulator returns savings via fixed multipliers (`0.52`, `0.523`, `0.75`, etc.) independent of provider, region, SKU price, runtime, storage, or valid transition.
- [ ] Downsizing predicts utilization by multiplying CPU/memory by reciprocal cost factor and clipping to 100%, without capacity metadata, peak percentile, or feasibility rejection.
- [ ] Fixed confidence values are presented like likelihoods; risk uses only projected mean utilization thresholds and lacks missing/short-history behavior.
- [ ] Recommendation engine evaluates only the latest observation per resource, despite daily historical records; labels/static percentages are not evaluated against withheld labels.
- [ ] Ranking is the same recommendation order and does not expose a savings-only comparator.
- [x] Forecast compares a seasonal-naive model, weekday median and Random Forest. Selection uses a chronological validation slice inside training; the later holdout is reported separately. Held-out fit remains weak and is disclosed.
- [ ] `/chat` handles keyword fragments; a question mentioning “cost increase” returns the first Isolation Forest outlier, not a quantified attribution for the user’s period.
- [ ] README/project report refer to documented cost factors and risk framework although the implementation has no configurable pricing catalog and the “factors” are action-wide constants.
- [ ] The dashboard simulator offers actions for every selected candidate even when actions are invalid for its resource/service.
- [ ] `/health` checks only process reachability, not the loaded data or database readiness.

### Missing

- [ ] Configurable provider/region/service/SKU resource and price catalog, billing models, and supported transitions.
- [ ] Multi-action what-if result with estimated utilization, constraint violations, workload coverage, assumptions, and insufficient-evidence warnings.
- [ ] Documented risk, confidence, and non-overlapping objective functions with tests for high-savings/high-risk versus safer alternatives.
- [ ] Storage and scheduled-shutdown calculations constrained by available observations and billing assumptions.
- [x] Held-out evaluation reports Isolation Forest, rolling-MAD, and their hybrid. The hybrid has higher recall on the seeded scenario, with more false positives.
- [ ] Measured root-cause contribution decomposition and uncertainty.
- [ ] PostgreSQL adapter/migrations/transactions/repositories for resources, observations, costs, recommendations, simulation runs, anomalies, predictions, and audit events.
- [ ] RAG corpus ingestion, chunk/index persistence, retrieval, citations, and source-grounded tests. Current docs correctly label RAG as future, but implementation is absent.
- [ ] Structured copilot intent handling for provider/service, forecast, risk, infeasible options, and explicit grounded evidence.
- [ ] Frontend multi-option comparison view, ranking comparison, and per-run assumptions/warnings.
- [ ] Frontend test suite and end-to-end workflow; Docker integration test and Postgres-backed API tests.

### Hard-coded values / risky assumptions

- [ ] Synthetic generator embeds INR rate assumptions and region multipliers; they are synthetic values and not actual market pricing, but should be named, versioned, and clearly surfaced.
- [ ] Recommendation save rates and simulator action multipliers are hard-coded; confidence percentages are fixed by threshold.
- [ ] Risk thresholds and score weights are embedded in Python and prose is inconsistent with implementation.
- [ ] Compose includes a static local demo database password; appropriate only for throwaway local environment.
- [ ] CORS allows arbitrary private-network hosts on Vite ports by default; wide development convenience should be opt-in/configurable.
- [ ] Upload has no size/resource cap and catches every exception as a 422; it writes cleaned data back to the default demo CSV.
- [ ] Dataset scenario labels are preserved in ETL, so feature code must explicitly isolate feature columns to prevent leakage.

### Highest-impact implementation order

1. Replace the multiplier simulator with validated catalog-based alternatives, explicit billing models, workload constraints, and evidence quality.
2. Build a shared risk/confidence/utility objective and paired savings-only/risk-aware ranking.
3. Add unit tests for pricing/action feasibility/uncertain evidence and scenario-level offline comparisons.
4. Add rolling anomaly baseline comparison and contribution-based root cause.
5. Make Postgres the authoritative repository for imports and API reads, keeping CSV as an import adapter.
6. Wire a structured analytics copilot and leave RAG explicitly unimplemented until ingestion/retrieval/citations are real.
7. Update simulator dashboard and setup/report docs, then validate backend, frontend, DB, and Compose paths.

## Security and data quality

The archive contains no API secrets. Main current risks are unbounded CSV parsing and file overwrite, static Compose credentials, broad dev CORS, no auth/tenant boundary, and in-memory process state. Data checks do not reject negative prices/costs, invalid network/storage values, invalid provider/SKU combinations, duplicate timestamps per resource, or sparse histories. Financial data is synthetic INR. There is no live cloud write path, which is appropriate for the demonstrator.
